## Build & Development Commands

```bash
npm run dev       # Start development server
npm run build     # Production build
npm run start     # Start production server
pnpm lint         # ESLint (next/core-web-vitals) — runnable since #7
pnpm test         # Unit tests (vitest, tests/unit — offline, Firestore faked)
pnpm typecheck    # tsc --noEmit
```

⚠️ **`pnpm build` is NOT a safety gate.** `next.config.mjs` sets
`eslint.ignoreDuringBuilds` and `typescript.ignoreBuildErrors`, so the build
passes with type errors *and* lint failures. Both flags are kept deliberately —
flipping them would make a lint regression a failed **production deploy** — so
the real gate is `.github/workflows/ci.yml` (#7), which runs typecheck, lint,
unit tests and the build on every PR. `react/no-unescaped-entities` is off in
`.eslintrc.json`: it is cosmetic, and the copy it flags is marketing text this
repo's brand rules say to keep verbatim.

Unit tests live in `tests/unit` (vitest, `vitest.config.mts`); the Playwright suite in `tests/e2e` is separate and staging-only.

## Architecture

**Next.js 15 (App Router) with React 19**, deployed on Vercel. Single web application (not a monorepo) for "POOL" — a group fund management service.

### Key Directories

- `app/` — Next.js app router: pages, layouts, API routes
- `app/api/` — API routes: `contact`, `preregister`, `questionnaire`, `location`, `update-site-visit`
- `lib/server/firebaseAdmin.ts` — server-only Firebase Admin SDK init (the ONLY Firebase entry point)
- `lib/waitlist/` — waitlist store (all Firestore reads/writes), request schemas, CSV encoding, types
- `components/` — Reusable React components; `components/ui/` is shadcn/ui primitives
- `lib/` — Utilities (classname merging, location detection, mobile helpers)
- `styles/` — Global and theme CSS

### Backend & Data

Two independent backends, deliberately kept separate:

- **Marketing site → Firebase Firestore** for the waitlist: `preregistered_users` collection, written by the public API routes (`app/api/{preregister,questionnaire,update-site-visit}`) and read by the waitlist admin screens. **Server-side only, via the Firebase Admin SDK** — see *Waitlist (Firestore)* below.
- **Platform-admin surface → the Pool API** (`api.poolapp.co` / `api-staging.poolapp.co`), a pure REST client — see *Platform-Admin Section* below.
- **Resend** for sending contact form emails.

### Waitlist (Firestore) — server-side only

- **The browser never talks to Firebase.** There is no Firebase client SDK in the app and no `NEXT_PUBLIC_FIREBASE_*` config. `lib/server/firebaseAdmin.ts` (`import 'server-only'`) initialises the Admin SDK from ONE server-only env var, `FIREBASE_SERVICE_ACCOUNT_JSON`, and **fails closed** (`FirebaseAdminUnavailableError` → 503) when it is missing or malformed — never falling back to another way in. The Admin SDK bypasses security rules, which is what lets the committed `firestore.rules` deny ALL client access; the rules file is the source of truth and is published by hand (README runbook).
- **All reads/writes are in `lib/waitlist/store.ts`**, which takes the Firestore instance as a parameter (unit-tested against `tests/unit/support/fakeFirestore.ts`). New entries are keyed by `sha256(normalized email)`, so a lookup is a point read; legacy random-id entries are found by an `email ==`/`in` query (`limit 1`). **Nothing on a public path lists the collection.** Read-modify-write runs in a Firestore transaction.
- **Public routes are allowlisted and enumeration-safe.** `lib/waitlist/schema.ts` strips unknown keys (stripped, not refused — returning visitors' saved progress can carry old-version keys), bounds every length (over-long text is CUT, code-point-safe, never refused — a refusal the form did not warn about is one a visitor can never get past; limits live in the dependency-free `lib/waitlist/limits.ts` so the form's `maxLength` uses the same numbers), uses the forms' own email shape rule rather than a stricter one, and keeps only the choice values the form offers (`QUESTIONNAIRE_OPTIONS` in `lib/questionnaire-questions.ts`, which the questionnaire page also renders from — one list, two readers). Every route answers identically whether an address is new, known or complete. An unauthenticated submission may FILL an entry's missing name/location but never replace it, and an empty answer never erases an earlier one. `update-site-visit` applies only with the one-time `siteVisitToken` the questionnaire response issued (stored as a sha256 hash, 1h, single use, never changes an answer already recorded).
- **Admin data goes through `app/admin/api/waitlist[/:id]`** (static routes, so they beat the `[...path]` proxy). `lib/admin/adminSession.ts` → `requireProductionAdminSession` is the gate: production selected, else 404; then it calls the same identity-gated probe login uses (`/admin/metrics/signups?days=1`) with the cookie's Bearer, refreshing once on a 401, and acts only on a 200 — so a forged or staging cookie cannot reach Firestore (middleware only checks cookie presence). DELETE also refuses a browser-flagged cross-site request and commits the delete together with a `waitlist_deletions` record (entry id, time, admin's Pool user id — no data about the deleted person). The admin DTO is an explicit projection (`toWaitlistEntry`), so the token hash and any later field never reach the browser.
- **CSV exports** go through `lib/waitlist/csv.ts` (`csvCell`/`csvRow`/`toCsv`): quotes doubled, and a cell starting with `= + - @ TAB CR` is prefixed with `'` so a spreadsheet shows it as text (CWE-1236). Every waitlist cell is written by the public.
- **Residuals (documented, not solved in code):** no rate limit in code (an in-memory counter is not a limit on Vercel — use a Vercel Firewall rule); nothing proves a submitter owns the email they type, so anyone can add questionnaire answers to an incomplete entry for an address they know (they cannot replace names/location or erase answers).

### Platform-Admin Section (REST client, #85)

The `/admin` surface is a **pure REST client of the Pool API** — no Firebase-for-data. Auth is **Email-OTP + httpOnly cookies behind a Next server-side proxy**; tokens NEVER touch client JS and browser calls stay same-origin.

- **Environment switcher — Staging ⇄ Production (#112)**: the dashboard is no longer single-environment. `lib/admin/adminEnv.ts` is the **pure, client-safe** vocabulary module (which environments exist, their cookie names, their badge styling) shared by the nav, `middleware.ts` (edge) and the server-only `serverApi.ts`, so the three can never disagree about what `production` means. **Sessions are PER-ENVIRONMENT and that is the whole safety argument**: a Pool JWT is only valid for the API that issued it, so every session cookie is namespaced (`pool_admin_at__staging` / `__production`, via `adminCookies(env)` — there is no unscoped session-cookie name left in the codebase) and there is no code path that reads one environment's token and sends it to another. `serverApi` has **no ambient environment and no zero-arg `apiUrl()`** — every call takes an explicit `ApiEnv`, and the proxy resolves it ONCE per request so the base URL and the token cookie cannot be chosen separately. `POST /admin/api/env` (a route beside the catch-all, so it needs no session — you must be able to leave an environment you cannot authenticate against) writes the `pool_admin_env` cookie and **nothing else**: it mints no token and moves none. That cookie **confers no authority** — tampering with it just points the proxy at an environment you have no cookie for, i.e. a 401 → that environment's login, which is also the intended UX. `middleware.ts` gates on the SELECTED environment's cookie and imports only the pure modules (edge runtime). **The QA console's server-side gate now reads the SELECTED env**, not a build-time constant — a compile-time check would leave it reachable after a runtime flip to production. **PRODUCTION is deliberately the loudest thing on the page** (solid red badge + red header rule + a confirmation step to switch INTO it); staging stays amber. Logout is **scoped to the selected environment** (`?scope=all` ends them all) and the button says so. **⚠️ No cookie migration**: the pre-#112 unscoped cookies carry no record of which API issued them, so they are swept up on logout and never adopted — everyone re-logs in once. `POOL_API_BASE_URL` is preserved as the **default environment**, so the "simple prod-flip" still works on its own; `POOL_API_BASE_URL_{STAGING,PRODUCTION,LOCAL}` override the built-in defaults.
- **Environment strip — the switch made unmistakable (web #14)**: the Phase-10 walkthrough found #112's badge easy to miss and its switcher effectively buried (far end of a nav row, same visual weight as everything else) — and on the LOGIN page both appeared only once a client fetch resolved, which is the one screen where guessing wrong costs an OTP that can never verify. `components/admin/EnvBanner.tsx` replaces both with a **full-width coloured strip rendered by `app/admin/layout.tsx` on BOTH branches** (signed in *and* login), from the SERVER-resolved env, so the environment is stated on the first paint of every page. Tone is the message: production solid red, staging amber, local muted (`ENV_BANNER` in `adminEnv.ts`), and each states the **consequence** ("real users and real money" / "test data only"), not just the name — a founder should not have to remember what "staging" implies at the moment they act. **There is now exactly ONE switcher in the dashboard**, on the strip, under an explicit "Switch to" label: it was removed from `AdminNav` (which keeps only the badge, as an echo for after the strip scrolls away) and from the login card (which keeps only the contextual "your code will be minted by X" sentence). `EnvSwitcher` gained a `surface="banner"` variant purely for legibility — the page palette (`bg-muted`, `text-muted-foreground`) is unreadable on solid red/amber, and the active pill's own environment colour would be invisible against a strip of the same colour, so on the banner the active item inverts to white and the production confirmation renders as a white card. **Plumbing is untouched**: same cookie, same `POST /admin/api/env`, same per-environment sessions, same confirmation step for switching INTO production. Presentation and placement only.
- **Auth flow** (`app/admin/api/auth/*` Route Handlers): `send-otp` → `verify-otp`. Both target the **selected environment's** API and write **that environment's** cookies. On verify, the server confirms platform-admin status by calling an identity-gated admin endpoint with the fresh Bearer (a non-admin JWT gets 403 → login rejected, no cookies). On success it sets httpOnly `pool_admin_at` / `pool_admin_rt` / `pool_admin_dt` cookies (`path=/admin`). `logout` best-effort revokes the device token and clears cookies. Cookie contract: `lib/admin/authCookies.ts`.
- **Proxy** (`app/admin/api/[...path]/route.ts`): same-origin catch-all. Reads the access-token cookie server-side, forwards GET/POST/PATCH/DELETE to `${POOL_API_BASE_URL}/api/v1/admin/<path>` with the Bearer. On a 401 it refreshes once via the refresh cookie, rewrites cookies, and retries. Because the browser→Next hop is same-origin and Next→API is server-to-server, **no poolmobile CORS change is needed**.
- **Guard**: `middleware.ts` gates `/admin/*` (excluding `/admin/api/*` and `/admin/login`) on the presence of the SELECTED environment's access-token cookie; `app/admin/layout.tsx` (server component) reads the same cookie to decide whether to paint the nav chrome, and additionally computes a per-environment "is there a session" boolean (presence only, never a token) for the switcher.
- **Client API**: `lib/admin/adminApi.ts` — typed fns over `fetch('/admin/api/<path>')`, no base URL/Bearer on the client, centralized 401 → `/admin/login`. DTOs hand-copied from poolmobile `@pool/shared` into `lib/admin/types.ts`.
- **Errors / Health tab** (`app/admin/errors`, poolmobile #192 over the #116 API): the READ surface for everything #26 made the API write. ONE endpoint — `GET /observability/errors` (static path, forwarded unchanged by the catch-all proxy; there is deliberately no `/summary` or `/sentry` route) — returns BOTH sources in a single **fail-open** payload, so the page's real job is that **an empty panel must never imply "nothing is wrong"**. Every panel carries a `SourceStatusNotice`; only `ok` licenses the words "no failures", and `disabled`/`unconfigured`/`unavailable` each say what was *not* queried. The signal tiles show **"—" rather than "0"** when the log source is untrustworthy (a zero from a source nobody read is a lie in the dangerous direction). The `bySignal` bar chart renders `SIGNAL_ORDER` **including zeros** — the API guarantees every key is present so a series never vanishes, and a signal at zero reads as *recovered*. The Sentry link-out is rendered from `issuesUrl` **independently of `status`** (the API returns it whenever the ORG SLUG is set, even with no read token, so an unwired token degrades to "open Sentry", not to a dead panel). ⚠️ **`path` / `message` / `errorMessage` / `requestId` are attacker-influenceable free text** (#116 review, L3/L4) — rendered as TEXT children only; no `dangerouslySetInnerHTML` on this surface, and no feed value is ever used as an `href`. The only hrefs are Sentry URLs, scheme-checked by `safeHttpUrl` (`href` still executes `javascript:`). Display vocabulary + the "why empty" copy live in `lib/admin/observability.ts` (a mirror of `@pool/shared`'s `OBSERVABILITY_FEED`, since this repo cannot import the poolmobile workspace; the API re-validates every bound with Zod, so drift degrades to a 400). Charts reuse the existing `components/ui/chart.tsx` convention — no new chart primitive, no new palette.
- **Health insights — the plain-language verdict (web #14)**: everything the Errors tab shipped with is correct and none of it answers the question a non-developer founder arrives with; a tile reading `Pool timeout (P2024): 3` presumes you know what a connection pool is. `HealthSummary` now sits **first on the page** and states one coloured verdict plus, underneath, every reason it is not green — worst first, each phrased as what a USER would have experienced ("some people were shown an error"), not what the log line said. The derivation is `lib/admin/health.ts` → `deriveHealth`, a **pure function of the two payloads the page already holds** (#116's errors feed + #190's alert state), so it can never disagree with the panels below it, and it **invents no endpoint and no metric**. ⚠️ **There are FOUR levels, and the fourth is the point**: `Unknown` ("can't tell") is used whenever a source could not be read — a null payload, a non-`ok` `ObservabilitySourceStatus`, or an alarm in `Unknown`/`InsufficientData`. Only a successfully-read source may license good news, so a failed read never renders green; that is #116's whole thesis, applied at the one place where the mistake would be made permanent. Thresholds (`HEALTH_THRESHOLDS`) are **display heuristics only** — the durable always-on counters are the CloudWatch metric filters behind #190's alarms — and are deliberately conservative at beta scale (any thrown error or any 5xx response is worth a line; a handful of lock-contention retries is not). `ALERT_KEY_PLAIN_LANGUAGE` gives each watched alarm — including **`BalanceDrift`**, which is a money problem that does not fix itself — a consequence-and-first-action sentence in a different register from the server's frozen `label`/`description` (which are still rendered verbatim in `AlertsPanel`); an alarm key the server adds later falls back to its own description rather than going silently unexplained. A new **"Signals no alarm covers"** card spells out the three WARN-level signals in ordinary words with a **per-code remediation** — P2028 (lock timings) and P2024 (pool sizing) are split precisely because their fixes differ, and collapsing them gets the wrong one applied — and shows **"—" not "0"** when the log source is untrustworthy, like the tiles. ⚠️ **The alerts fetch moved out of `AlertsPanel` into `useAdminAlerts`** (page-level, passed down as props): two independent pollers a few seconds apart could put "everything looks healthy" directly above a row reading IN ALARM. The layout's `CriticalAlertBanner` keeps its own poller — it is mounted on pages that never render this hook, and its job is to interrupt rather than to inform. Refresh refreshes **both** halves, and the strip spins until both have resolved once (a verdict derived from one would flash "could not be read" for the length of the other request).
- **Per-user logs** (`app/admin/user-logs`, web #14 over the poolmobile #263 API): the support/debug pull — pick a person, pick a bounded window, get their request logs, audit trail (in BOTH directions: what they did, and what was done to them) and app events merged into one newest-first timeline. `GET /observability/user-logs?userId=&hours=&limit=` (static path; the id travels as a query param), forwarded unchanged by the catch-all proxy. ⚠️ **REQUEST-ON-DEMAND, AND NOT AS A UI PREFERENCE**: nothing is fetched until Fetch is pressed and there is **no polling and no auto-refresh anywhere on the page**, because the endpoint is **AUDITED ON VIEW** server-side (`admin.user_logs_viewed`, target = the named user) — a background poller would write an audit row every interval asserting a founder looked up that person's history when nobody did. The source-filter chips narrow what was already fetched and never re-query, for the same reason. **The three sources are labelled and NEVER flattened into one "event"** (`USER_SOURCE_COPY` carries each one's *authority*): `audit` is server-authored inside the mutation's own transaction (if the row exists, the write committed) and **deliberately retains money in integer cents and #146 payment handles**; `logs` is the API's own account of a request, allowlist-projected exactly as #116; `analytics` is **client-supplied**, already stripped of PII/money/coords at ingest (#24), and therefore the least authoritative — good for "what screen were they on", never proof. Each source **fails open independently**, so a missing CloudWatch IAM grant still returns the audit trail and the page says which half is missing — the four-status `SourceStatusNotice`/`Pill` vocabulary was widened to cover `audit`/`analytics` rather than forked. Ordering uses the SERVER's ingest time; an analytics row whose device clock disagrees says so inline. `AuditLogEntry.action`/`targetType` are typed as **strings, not mirrored enums** — `AuditAction` is an open ~80-member vocabulary, and a stale mirror would blank exactly the newest action someone is trying to understand; the wire values are already legible. ⚠️ Audit `metadata` and analytics `props` are arbitrary objects rendered as TEXT children (JSON-stringified when nested) — the #116 L3/L4 rule at full strength: no `dangerouslySetInnerHTML`, and **no payload value is ever an `href`/`src`**; the only link is an internal `/admin/users/<id>` built from the id the admin picked. The response's own `userId` is echoed in the header (never local state) so a row cannot be attributed to the wrong person, and re-picking a user without re-fetching shows an explicit "showing a different user" warning. Bounds mirror `OBSERVABILITY_USER_LOGS` (24h default / 7-day cap; limit is **PER SOURCE**, said out loud in the copy since a "100" can return 300 rows). **`UserPicker` moved from `components/admin/qa/` up to `components/admin/`** — a picker every admin screen shares must not live inside the staging-only console's folder.
- **Critical-alert banner + alerting status (poolmobile #190, server half PR #211)**: `GET /observability/alerts` (identity-gated, **no query params** — the watched alarm set is a fixed reviewed list server-side) drives two things. **`CriticalAlertBanner` is mounted in `app/admin/layout.tsx`, not on a page** — an alarm firing while you read the Users table is exactly the case a tab cannot cover — inside the `hasSession` branch so it never appears on login, and with **no `env` prop**: it rides the same env-aware proxy as everything else, so it follows the #112 toggle for free and always reports the environment the badge names. It renders **only** when `criticalCount > 0` (a banner that is always present is a banner nobody sees; every other state is explained on the Errors tab), styled to match the #112 PRODUCTION chrome so "solid red across the top" means the same thing twice. **A failed poll never clears a known-critical state** — only a definitive successful read with `criticalCount === 0` takes it down (the house asymmetry: only a definitive answer may destroy state); polling pauses on a hidden tab and re-reads on return. **`AlertsPanel` sits above the filters on the Errors tab** (live state, not a query result — none of the feed filters apply to it). Honesty rules are #116's one level down: **`AdminAlarmState.Unknown` is NOT `ok`** — CloudWatch not returning an alarm means *nothing is watching that failure mode*, a live possibility on prod until #53, so it renders as **"Not reporting"** with a warning tone; a non-`ok` `status` renders "do not read the rows below as all-clear"; and **a quiet inbox is always explained** via `email.status` (`environment_not_eligible` is staging's normal, permanent state and must not read as a fault), with `recipientCount === 0` called out **even when armed** — an alerter with no recipients is silently useless. `stateReason` is rendered **here and only here** (it exists nowhere else in the product — the alert email deliberately carries no upstream text), as a plain text child like every other upstream string. **`label`/`description` are the SERVER's frozen copy**, so this repo carries no alarm map and a newly watched alarm arrives correctly labelled with no web deploy. Poll interval `ALERT_POLL_INTERVAL_MS` = 60s — the alarms evaluate on a 5-minute period, so faster cannot make the data fresher. **No new env vars.**
- **Moderation queue** (`app/admin/moderation` + `[id]`, web #13 over the poolmobile #158 API): the **store-review gate's third requirement** — Apple Guideline 1.2 and Play's UGC policy want a block mechanism, a report mechanism and **demonstrable ACTION on reports**; the server shipped the first two and the write half of the third, and until this screen existed a filed report went into a table nobody could see. Three endpoints, all identity-gated (`GET /reports`, `GET /reports/:id`, `POST /reports/:id/review`), forwarded unchanged by the catch-all proxy. **The queue is OLDEST-FIRST and is never re-sorted client-side** — every other list in the product is newest-first because those are feeds; this is a work queue with a published SLA, so the row nearest its deadline is the oldest one, and re-sorting it into a feed would starve exactly the tail the commitment exists to protect. Pagination is the API's cursor (`nextCursor` over `createdAt ASC, id ASC`), appended never merged. The filter defaults to **Open**; since the API takes one status at a time, the header always shows the API's `openCount` (**open + reviewing**) so a report moved to `Reviewing` cannot quietly disappear from view. **SLA countdown**: `REPORT_TURNAROUND` (triage 24h / resolution 72h) is **mirrored** in `lib/admin/moderation.ts` — the admin DTOs deliberately don't carry it (only the reporter-facing `ReportReceipt` does), so it is a mirror with a pointer at the source of truth, like `lib/admin/observability.ts`. Both clocks run from `createdAt` (when the reporter was promised a turnaround, not when someone looked); triage is the transition out of `Open`, resolution the transition into a terminal state; **a resolved-late report still renders as breached**, because a breach that vanishes on close makes the promise unauditable. The SLA math is pure and takes `now` as an argument, so one page-level clock drives every badge. **Snapshot vs live content is the page's main honesty job**: `contentSnapshot` is the D2 evidence copy frozen at report time — it survives the sender deleting their account, an admin redaction, and the conversation itself — and it is labelled as such, kept visually separate from the reporter's own words (`details`, an accusation, not a finding). ⚠️ `details` / `contentSnapshot` / `reviewerNotes` are **user-authored free text written by people under review** (the #116 L3/L4 rule at full strength): TEXT children only, never `dangerouslySetInnerHTML`, never an `href` or `src` — the only links are internal `/admin/users/<uuid>` routes built from server-derived ids. **Review actions mirror the server's split exactly**: `CONTENT_REMOVED` is the one action the API *performs* (sets `Message.deletedAt`, D9, in the review's transaction) and is **message-target-only** — the option is disabled with a reason rather than 400ing after the click, and it is behind a `window.confirm` that states the redaction does *not* touch the evidence snapshot; `USER_SUSPENDED`/`USER_WARNED` are **recorded only**, and the panel says so and **links to `/admin/users/[id]`** instead of calling suspend itself (the server's delegate-don't-reimplement rule, mirrored in the UI — a duplicated suspend here would fork a governance write that already has its own transaction, its own audit action and its own refusal to suspend a platform admin). Notes are omitted from the body when blank so an empty box preserves a previous reviewer's notes instead of erasing them. Nav entry sits beside Users/Pools and is shown in **every** environment — a report queue that only exists on staging is not "demonstrable action".
- **Screens**: `app/admin/stats` (see *Stats* below — it replaced `app/admin/overview`, which is now a redirect), `app/admin/users` + `[id]` (list/search + suspend/restore + feature-flag toggle + the #84 **View as** dialog — see below), `app/admin/pools` + `[id]` (list + suspend/restore + read-only ledger #82), `app/admin/moderation` + `[id]` (reports queue + review, see above), `app/admin/feedback` (in-app feedback inbox, see below), `app/admin/errors` (Errors/Health, see above), `app/admin/user-logs` (per-user timeline, see above). - **Support — answering in-app support from the dashboard (web #45 over poolmobile#683)**: `app/admin/support`, a thread list beside a reader and a composer, so a founder no longer has to sign into the MOBILE APP as `support@poolapp.co` to answer. ⚠️ **THE PAGE'S REAL JOB IS ITS EMPTY STATE.** `MESSAGING_ENABLED` defaults OFF and the API 404s all three routes when it is — **before** the identity gate — and it answers identically when no support account exists yet, so an absence on this page is ambiguous between *"messaging is off here"*, *"nobody has ever opened a thread"* and *"the queue is clear"*, and **only the last is good news**. A 404 renders as a stated amber explanation naming `MESSAGING_ENABLED`; only an ANSWERED empty list is allowed to read as "nobody is waiting". Mutation-checked. ⚠️ **MESSAGE BODIES ARE USER-AUTHORED FREE TEXT** — the #116 L3/L4 rule at full strength: TEXT children only, no `dangerouslySetInnerHTML`, and **no message value is ever an `href` or `src`**; the only links are internal `/admin/users/<id>` routes from server-derived ids. A `deletedAt` (#158 D9 redaction) or `hiddenByBlock` message arrives with `body` **already stripped server-side**, so the bubble renders the STATE — "This message was removed." — never a blank bubble that reads as a message saying nothing. ⚠️ **THE THREAD CANNOT SHOW WHICH ADMIN REPLIED** (the sender is the shared account) and the composer says so out loud rather than implying a byline: the server's `admin.support_replied` row is the record. - **Feedback inbox (poolmobile #720)**: `app/admin/feedback` over `GET /admin/feedback` (filters `status`/`area`/`kind`, cursor = previous page's `nextCursor`) and `POST /admin/feedback/:id/status` (`{ status }`; same-status is a server no-op, unknown id 404s), both identity-gated and forwarded unchanged by the catch-all proxy. - **Stats — the tabbed replacement for Overview (web #33)**: `app/admin/stats` is the one page that answers "what does the whole site's data look like". It keeps EVERY figure the Overview showed and adds the #624 widenings (pool categories, size buckets, the public/private split, settlements, the #251 points economy); the Overview route survives only as a redirect, because it was the landing page for months and a 404 on a bookmark reads as "the dashboard is broken". Seven tabs — Growth · Activity · Pools · Money · Engagement · Funnels · Health — each a `<section aria-labelledby>` that **states its own scope**, because three of the seven are NOT scoped by the range control and a reader who assumes otherwise misreads every number under them. ⚠️ **ONE FETCH, ONE RANGE, MANY TABS**: every panel is fed by a single `Promise.allSettled` over the same window, so two tabs can never answer the same question differently and clicking through them costs the rate-budgeted admin API nothing; only the range re-reads. Failure is **per panel** (`allSettled`, never `all`) and the whole-page error card appears only when EVERY metrics call failed. ⚠️ **Every #624 field is OPTIONAL in `lib/admin/types.ts`, exactly as #618's are**: the #112 switch can point the page at an older API, and each panel distinguishes "this API version does not report that" from "the window is empty" from "the call failed". **Two panels are empty BY DECISION and say which**: money volume in cents (founder decision D1, poolmobile#647) and the DAU/WAU/MAU trend (poolmobile#648 — `lastActivityAt` is one mutable column, so there is no history to plot). The Engagement tab's **leaderboard headline** is now live over poolmobile#681: ⚠️ it takes a board PERIOD, not the range control's `days` — two different axes, mapped explicitly by `boardPeriodForDays` with the period it used stated on the panel — its `value` carries a per-board NOUN (expenses on one board, DAYS on another, so a bare number would be read as the wrong thing), and an EMPTY board renders "no pool qualifies yet" rather than a zero, because the server reports empty boards rather than omitting them. Tiles carry a delta against the previous window, which arrives in the SAME response (`previousWindow` + `previous…` twins) — no second request per tile — and `—` vs `0` keep the Errors tab's meaning: a zero from a source nobody read is a lie in the dangerous direction.
- **Geography + city filters (web #33 Part B)**: the Stats page's **Geography** tab answers "where are our users and pools" from `GET /admin/metrics/geography` (#624) — users and pools by canonical city key (#128/#469, so one city is one row however it was spelled), a country and US/CA-region roll-up, and the counts for cities with no location at all. A **Users/Pools toggle** re-ranks every panel, because the response is sorted by the two combined and a pools view that kept that order would be wrong. ⚠️ **THE PRIVACY LINE IS THE SERVER'S AND THIS PAGE CANNOT WEAKEN IT**: site-wide user geography is CITY-LEVEL COUNTS ONLY — the endpoint's user query selects no coordinate, so there is no individual location here to leak — and the only exact points anywhere are PUBLIC pools whose owner opted into showing their venue (#21), which Discover already publishes. Individual coordinates stay on the audited user detail. ⚠️ **THE MAP IS NOT BUILT AND THE PANEL SAYS WHY**: the tiles CDN serves ranged reads correctly (206, correct `content-range`) but returns no `Access-Control-Allow-Origin` and 403s the OPTIONS preflight, so any browser renderer would be blocked — it needs a `terraform apply` on `infra/map-tiles/` (poolmobile#649). `maplibre-gl` is deliberately NOT a dependency yet; shipping it now would give a blank canvas failing in the console instead of a panel that explains itself and reports how many cities are ready to plot. **Users and Pools lists** gain a **City column** (display name, canonical key in the `title`, never coordinates) and a **city typeahead** (`components/admin/CityFilter.tsx`) that reads the city list once per mount. ⚠️ **THE KEY IS OPAQUE AND TRAVELS UNCHANGED** — `?city=` carries exactly what the geography response published, never re-derived from a display name and never normalized, because the server matches by equality and pre-#128/pre-#469 legacy keys are published too: tidying a key would make exactly those cities unfilterable, and silently. That is why the filter is pick-from-a-list rather than free text, and why a failed city list disables the control and says the rows below are *unfiltered*, not empty.
- **Creating a user / a pool from the dashboard (web #46 over poolmobile#684)**: `New user` on the Users list and `New pool` on the Pools list, both audited-by-contract (a required free-text reason). ⚠️ **NEITHER ENDPOINT EXISTS YET** — `POST /admin/users` and `POST /admin/pools` 404 on every environment as of 2026-09-18, so this UI is built against a contract pinned on poolmobile#684 and **today every attempt takes the not-served-yet path**. That path is the reason `lib/admin/adminErrors.ts` exists: `describeCreateFailure` turns a status into a sentence a founder can act on, and a 404/405/501 renders as an amber *"this environment's API cannot create users yet (poolmobile#684) — nothing was created, and nothing you typed was wrong"*, not a red failure implying the dashboard broke. It self-heals the day the endpoint ships. ⚠️ **A 5xx deliberately does NOT say "nothing was created"** — a gateway timeout may mean the write landed, and claiming otherwise is how a duplicate gets made on the retry. ⚠️ **`isNewUser` is load-bearing**: the server endpoint delegates to `findOrCreateUserByEmail`, which is find-**or**-create, so the success state says *"this account already existed"* rather than reporting a creation that did not happen. The user dialog states the three things the mental model "I made them an account" gets wrong (they claim it by OTP; it lands un-activated and shows in the activation metric; it grants no access — that is `View as`). The pool dialog **requires an explicitly picked owner** (an admin-owned pool is a support artefact nobody else can govern) and creates **PRIVATE** pools, because `createPoolSchema` requires a public one to carry a short description AND a canonical city that #194 makes picker-only — this dashboard has no such picker, and the owner flips it in-app. Money is parsed to integer cents by the shared string parser, never `parseFloat * 100`. **`/admin/users` and `/admin/pools` are now server shells** (`page.tsx`) that resolve the selected environment and hand it to a client `…Screen`: the dialogs name the environment they are about to write to, and the env cookie is httpOnly on purpose.
- **The admin nav is a HAMBURGER below `lg`**: at phone width eleven destinations in one `overflow-x-auto` row read as a scrunched, half-cut strip. `AdminNav` now renders two branches from one set of pieces (`Brand` / `NavItemLink` / `SignOutButton`, so the two layouts cannot disagree about the active rule or the labels) — a bar with the wordmark, the environment badge and a toggle, and a full-width panel of destinations. ⚠️ **THE ENVIRONMENT BADGE STAYS ON THE BAR, never inside the menu**: it is the #112 SAFETY signal, and a signal you have to open a menu to see is not one. The panel closes on Escape, on an outside click, and **on `pathname` changing** — keyed on the path rather than on a link's `onClick`, because the QA console and the env switcher both navigate programmatically and a menu left open over the page you just landed on is what makes a hamburger feel broken. ⚠️ **BOTH BRANCHES ARE IN THE DOM** (the desktop row is `hidden lg:flex`), so a role query matches only the visible one — `display:none` is out of the accessibility tree — while a bare TEXT query matches twice; tests use roles, or `.first()`.
- **Phone width is a tested property of the admin tables (web #33)**: the lists and the Geography table **shed columns below `sm`/`md`, and the row ACTION is never one of them**. The defect that forced this is worth keeping: at 390px the Users list rendered six columns, so `View` — the only control that makes a row useful — sat past the right edge of an `overflow-x-auto` box with no affordance, leaving rows readable and un-openable. What yields is what is derivable or secondary (email, joined date, visibility, member count, a city's region/country, the "new" column); what never yields is the identity, the money figure, the city (it is the filter's own feedback) and the link. `tests/e2e/admin-offline/mobile.spec.ts` asserts both halves at 390px — the document never scrolls sideways, and the action is `toBeInViewport`, **not** `toBeVisible`, because a control pushed past the right edge of a scroll box is "visible" to Playwright and unreachable to a thumb. `useNarrowViewport` exists only for sizes a class cannot express (recharts takes its axis width as a number prop); anything expressible as a responsive class stays one.
- **The chart colour system (web #33)**: `lib/admin/charts.ts` is the ONLY place a chart colour is named — roles, not hexes, everywhere else. It carries the validated categorical palette (eight hues in their documented order, which IS the colour-blindness mechanism), the semantic roles (lifecycle status matching the tables' badges, settlement/transaction status, delta direction) and the "why is this panel empty" vocabulary. The values themselves are mirrored into `app/globals.css` as `--chart-*` custom properties in the `:root` / `.dark` scopes, so a theme flip repaints every chart with no React state and no hydration flash; **`tests/unit/admin/chart-palette.test.ts` fails if the two copies drift**. ⚠️ **Long vocabularies deliberately get ONE hue**: `PoolCategory` has 16 members and `PointReason` ~20, and eight CVD-safe hues cannot be stretched to sixteen — those are horizontal bars with labelled axes, where bar length does the work. Fixed per-value colours exist only for the small closed vocabularies that recur across panels. Three light-mode slots sit below 3:1 on white, so every chart ships a labelled legend and the exact number as text — colour is never the only channel. Chart primitives live in `components/admin/charts.tsx`; the per-tab panels in `components/admin/stats/`.
- **Detail pages are grouped section cards over the poolmobile #618 contract (web #31)**: `/admin/users/:id` = Identity · Location · Profile · Engagement · Payment handles · Memberships (+ a Staging-context card that exists ONLY when `seedCohort`/`demoMode` is present, so production pages carry no trace of it); `/admin/pools/:id` = Identity · Location · About · Money · Lifecycle · Members, then the unchanged ledger tabs. The two pages **cross-link** (a member row → its user page, a membership row and the creator → the pool/user page). Shared kit in `components/admin/detail.tsx` (`DetailCard`/`Field`/`ChipList`/`TextBlock`/`Unreported`). **Country + region + city derive from `locationCityKey`** (`lib/admin/cityKey.ts` parses `name|region|country`, #128/#469; country name via `Intl.DisplayNames`) — coordinates are rendered as their own sensitive-tier row, never used to answer "where". ⚠️ **Every #618 field is OPTIONAL in `lib/admin/types.ts` on purpose**: the #112 switch can point either page at a production API that predates #618 (it has never been dispatched), and `hasRichUserDetail`/`hasRichPoolDetail` (presence of a key the widened select always emits) decide whether a section renders rows or the one-line `Unreported` note — never a column of dashes that reads as "this person has no profile". Field names are the Prisma column names #618's allowlist select emits (the contract is pinned as a comment on poolmobile#618), so wiring the data on is a server deploy, not a second frontend change. ⚠️ The widened user read is **audited on view** server-side (`admin.user_detail_viewed`, #618's decision 2) — the user page fetches once per visit and after an explicit action, never on a timer (the #263 user-logs rule).
- **View as — copy feedback (web #30)**: `Copy token` in `ViewAsDialog` ends in one of two VISIBLE, DISTINCT outcomes — `Copied` or `Couldn't copy` (destructive tone + a manual ⌘C fallback line, and the token is selected) — both reverting after a dwell so the control stays reusable, and both announced through a polite `role="status"` live region that is mounted BEFORE its text changes (a live region inserted with its message is routinely not spoken). An absent `navigator.clipboard` (non-secure context) lands on the same failure path as a rejection. This is the one copy in the product that must never be silent: the token is shown once and closing the dialog destroys it (poolmobile #222's no-silent-outcome rule at its highest-stakes instance). Covered by `tests/e2e/admin/view-as.spec.ts`, which — unlike every other admin spec — WRITES (one audited 15-minute session per run, ended by the spec through the Admins page).
- **Waitlist screens** (`app/admin/dashboard`, `app/admin/dashboard/stats`) are **production-only** (server page gate, poolmobile #602) and read their data from the gated `/admin/api/waitlist` routes — see *Waitlist (Firestore)* above. They are linked from the admin nav as "Waitlist" (production only).
- **QA console — STAGING ONLY** (`app/admin/qa`, poolmobile #132): a founders' console to trigger notifications, run scheduled jobs, drive multi-user workflows, set up state and inspect a user, instead of waiting on timers or contriving real events. Tabbed (Notifications · Jobs · Workflows · State · Inspect); components in `components/admin/qa/`, calls isolated in `qaApi` (`lib/admin/adminApi.ts`) + DTOs in the QA block of `lib/admin/types.ts`. All routes are namespaced `/qa/...` so the existing catch-all proxy forwards them unchanged — **no proxy change**. **Visibility is double-gated:** the page 404s server-side when `getApiEnv() === 'production'`, and the authoritative check is the API — **`GET /qa/status` returns 404 whenever the console is disabled server-side**, which the client treats as "disabled" (renders nothing, redirects to Stats). The nav entry (`NON_PROD_NAV_ITEMS` in `AdminNav`) is convenience only, never the gate. Guarded controls (broadcast-to-all, reseed, wipe, reset-account, force-pool-status) each require their own typed confirmation phrase **plus** `window.confirm` — the five phrases differ so a typo in one box can never trigger another action, and each is compared with strict equality (no trim/case-folding) exactly as the server does. Push/broadcast copy is additionally checked client-side against the API's money-free-copy rule (no currency symbols, decimal amounts or @handles on a lock screen). Two results get deliberately non-standard rendering: **reset-account resolves 200 with per-step failures inside it** (it is not atomic — a refused `leave_pool` on a pool OWNER is the normal case), so `steps[]` is always rendered per-step rather than as a flat success; and **force-pool-status is the one endpoint that bypasses the delegate-to-real-code rule**, so its returned `warning` is rendered verbatim in a `destructive` Alert at the same weight as the destructive controls.

## Brand System — "sticker-pop" (mandatory for all UI work)

Pool is a **social network** for friend groups who spend time and money together — never describe or style it as a bill-splitting/expense/fintech app. The visual world: a kiddie pool with three stacked rings, money splashing in, thick navy outlines, flat fills, no gradients on illustration.

### Color tokens (Tailwind names / CSS vars in `app/globals.css`)

```
pool-blue   #4EC3F5   top ring, links, sky sections
pool-yellow #FFCE3E   middle ring, primary buttons
pool-pink   #FF77B0   bottom ring, pre-register CTA
pool-green  #63C666   bills, success
pool-gold   #F5B63C   coins
```

Rules: navy is the only text color on light backgrounds (use navy at reduced opacity for hierarchy — never gray). No gradients, no purple/indigo, no glassmorphism, no blurred blobs, no soft `shadow-lg`. White text on yellow is banned (fails contrast).

### Sticker construction (the unifying device)

Every interactive/card-like element: 2.5px solid navy border · hard offset shadow `4px 4px 0 var(--navy)` · radius 12–20px (pills for buttons) · hover lift `translate(-2px,-2px)` + 6px shadow · active press `translate(2px,2px)` + no shadow. Use the primitives: `.sticker`, `.btn-sticker` + `.btn-{yellow|blue|pink|ghost}`, `.chip-sticker`, or the `StickerButton`/`StickerCard`/`Chip` components in `components/sticker.tsx`. Transition `transform` only — never animate `box-shadow`, `filter`, or layout properties.

### Type & marks

- Display: Baloo 2 (`font-display`, weights 700/800) for H1/H2/wordmark only. Body: DM Sans (`font-sans`). Both via `next/font/google` in `app/layout.tsx`. Never use the display face for paragraphs.
- Brand marks are inline SVG in `components/brand/marks.tsx` (`PoolMark`, `Coin`, `Bill`, `Droplet`, `Splash`, `CloudMark`, `Wordmark`). Never scale the PNG logo for UI.

### Copy rules

- Keep verbatim: "Pool. Tap. Done." · "A social network for people who spend time — and money — together." · "WTF Is Pool?!" · "Ready to Jump In?" · "no IOUs, no awkward math, no receipts to chase."
- Banned in feature copy: split/splitting, settle/settling, expense(s), tracking-as-feature, fintech, seamless, effortless, elevate, unlock, empower. ("No IOUs / no tracking" as negation is allowed.)
- Voice: warm, direct, a little cheeky; short sentences; crews/moments/routines — never transactions or "financial wellness". Emoji only inside feed/ticker content, never as heading decoration.

### Motion & a11y budget

Animate `transform`/`opacity` only; all loops pause offscreen (IntersectionObserver) and on `visibilitychange`; `prefers-reduced-motion` gets static scenes; visible navy focus rings everywhere; decorative SVGs `aria-hidden`.
